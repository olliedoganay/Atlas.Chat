# Atlas Chat v1.3.0

Release date: 2026-08-20

Atlas Chat 1.3 makes local-model startup understandable, turns Python GUI execution into a secure offline workflow, and hardens run recovery, profile privacy, persistence, shutdown, and dependency verification across the desktop stack.

## Model startup and run visibility

- Run progress now names the real phase: memory lookup, model startup, generation, memory persistence, compaction, cancellation, or failure. Cold model loading no longer appears as an unexplained “Deciding” state.
- Run Details remains available even when a model emits no reasoning trace and reports the current model, stage, elapsed time, and terminal error honestly.
- Ollama memory embeddings run on CPU with an ephemeral keep-alive policy so the embedding model does not evict a large chat model from limited VRAM. Empty memory collections skip unnecessary embedding work.
- Local chat calls have a bounded five-minute request timeout while still allowing proven cold hybrid model loads to finish.
- Discovery uses model size together with available GPU and system memory to label full-GPU, hybrid, and constrained fits more accurately.
- Active chats can recover their authoritative backend run after a webview reload without resurrecting stale or terminal runs.

## Secure offline Python GUI runtime

- Pygame code now uses a versioned Atlas runtime containing hash-locked `pygame==2.6.1` and `numpy==2.5.2` instead of attempting `apt` or `pip` inside the submitted-code container.
- Trusted runtime preparation is asynchronous, visible, deduplicated, and never mounts or executes submitted source.
- Submitted GUI code runs separately as UID 65534 with a read-only root filesystem and source mount, no added capabilities, `no-new-privileges`, and an Atlas-owned internal preview network with no outbound route.
- Unsupported GUI dependencies fail before execution with an actionable explanation; Atlas never weakens `ATLAS_RUNNER_NETWORK=none` automatically.
- Failed runs offer **Fix with Atlas**, which creates a bounded, profile/thread-scoped, reviewable repair draft containing the source and useful diagnostics. It never silently changes or submits code.
- **Rerun same source** now says exactly what it does, and assistant Retry branches before the target prompt instead of duplicating that user message.
- Small game and visual-app requests prefer a self-contained offline HTML preview unless Python or another framework is specifically requested. Atlas no longer calls unexecuted code “tested” or “ready-to-run.”

## Reliability, persistence, and cancellation

- Persisted answer and reasoning fragments are coalesced into bounded UTF-8 chunks while live SSE delivery remains immediate. Logical sequence ranges preserve exact reconnect ordering.
- Streamed output is capped at 2,000,000 UTF-8 bytes and persisted event history at 8,192 entries; pathological one-character streams no longer cause near-quadratic artifact rewrites.
- Same-thread queued runs refresh their history/search positions when execution actually begins.
- OpenAI-compatible cancellation cannot accidentally start a fallback request after the user stops a run.
- Memory persistence is best-effort after a successful answer: a Mem0 write failure is surfaced as a warning without discarding the generated response.
- Shutdown is now two-phase, so Atlas quiesces work before Uvicorn drains and closes encrypted checkpoint resources only after request serving ends.
- Corrupt active-run artifacts are quarantined and replaced with a sanitized failed record instead of preventing the backend from starting.

## Profile privacy and desktop recovery

- Profile lock, delete, and reset purge the corresponding cached histories, contexts, runs, memories, searches, drafts, attachments, titles, and live-run state from the renderer.
- Composer drafts are isolated by profile and thread. Switching identity cannot carry private text or attachments into another chat.
- Profile-scoped backend reads and stream subscriptions participate in the same lifecycle gate as mutations, preventing lock/delete races from returning protected content.
- Diagnostics no longer renders cached prompts for a locked profile.
- Provider keys are preserved only when the provider remains unchanged, and provider restart controls are blocked while either chat or code-runner work is active.
- User-requested cancellation is presented as a neutral cancelled state; a failed Stop request keeps the live stream attached and recoverable.

## API, attachment, and runtime hardening

- The backend enforces the 40 MiB request limit while reading the ASGI body, including chunked requests without `Content-Length`.
- Base64 attachment sizing accounts for padding correctly. Image uploads require an explicitly supported media type and matching file signature.
- Frontend backend URLs remain loopback-only, requests have bounded timeouts, and a stale cached status cannot leave the shell showing Ready after the backend fails.
- Mem0 lazy initialization and close/reset are serialized, and local Ollama clients preserve the loopback, redirect, and proxy protections.
- Model context-window changes and unload requests are rejected while chat work is active rather than closing a provider beneath a generation.

## Dependencies, CI, and release verification

- Python, npm, and Cargo locks include current security fixes; local audits report no known Python or npm vulnerabilities and no blocking Rust vulnerabilities. Documented upstream GTK/Tauri maintenance and soundness warnings remain.
- The tagged release workflow now runs the same Python, npm, and Cargo dependency audits before any installer can be published.
- The offline GUI runtime definition is included in Python wheels and the PyInstaller/Tauri backend-resource configuration.
- Frontend recovery, runner, privacy, provider, cancellation, and run-progress contracts have focused regression coverage alongside expanded backend stress and lifecycle tests.

## Upgrade notes

- Existing Atlas profiles, chats, encrypted stores, and encrypted run artifacts remain supported. Very old plaintext run data requires the explicit one-launch migration opt-in documented in the README. An unreadable active artifact is moved into the private quarantine directory rather than deleted.
- Chat-provider endpoints must now resolve to the same-machine loopback interface (`localhost` or a numeric loopback address). Existing LAN or remote provider URLs are rejected; expose or tunnel that runtime through a local loopback endpoint before configuring Atlas.
- The first Python GUI run on a machine prepares the trusted Atlas image and therefore needs one-time image/package download access. Subsequent submitted Pygame runs remain offline. The prepared image is approximately 837 MiB uncompressed.
- Docker remains optional for chat and HTML preview, but is required for server-side code and Python GUI execution.
- Keep `ATLAS_RUNNER_NETWORK=none` unless submitted code explicitly requires outbound access. Atlas-owned runtime preparation is separate from submitted-code execution.
- macOS community builds remain unsigned and unnotarized; the first launch may require manual approval in Finder.

## Release-candidate verification

The v1.3.0 candidate completed the full backend, frontend, Rust/Tauri, dependency-audit, version, workflow, packaging-configuration, and live offline Pygame runner gates. Tagged GitHub builds repeat the cross-platform verification before publishing installers and SHA-256 checksum manifests.
